# co2-vent — «Вентиляція класу» (ПЗІР, курсова, варіант 20)

Сидорук Артем, КІ-404. Маршрут **А — локальний програмний симулятор** (методичка, п. 5.2).
Модельований вузол: Arduino Uno + ESP8266, 3 × SCD40 (CO₂), Wi‑Fi → MQTT. Усі дані мають
`source=simulated`: це сценарні значення, а не фізичне вимірювання.

Є два джерела даних з однаковим контрактом і спільним сервером:
1. **Простий симулятор** (`simulator.py`) одразу публікує JSON. Через нього перевіряються контракт і відмовні вставки.
2. **Емульоване залізо** (`hw/`, контейнер `hw`). Справжня прошивка Uno, скомпільована `arduino-cli`, виконується в simavr.
   - **Давачі:** прошивка читає моделі TCA9548A і 3 × SCD40 через I²C на рівні байтів.
   - **Зв'язок:** рядки по UART передаються в модель ESP8266, яка публікує їх у MQTT.
   - **Виконавець:** команда проходить шлях ESP → UART → Uno → пін реле D7 → ACK.
   - **Без змін для плати:** та сама прошивка (`hw/firmware/uno_node/uno_node.ino`) прошивається в реальний Uno. Див. розділ «Емульоване залізо».

**Правило варіанта 20:** медіана трьох SCD40 > 1000 ppm безперервно 3 хв → `ventilation_on`;
медіана < 800 ppm → `ventilation_off`.

## Середовище

macOS 26 / Linux, Python 3.11+ (перевірено на 3.14.7), Docker (брокер `eclipse-mosquitto:2`),
`paho-mqtt==2.1.0`, SQLite зі стандартної бібліотеки. Хмара й платні сервіси не потрібні.

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp config.example.env .env      # за потреби змінити; секрети - лише тут/в env
```

## Запуск

```bash
docker compose up -d                       # брокер на 127.0.0.1:1883
.venv/bin/python make_scenario.py --seed 20 # (пере)створити scenarios/class_day.csv
```

Окремі термінали (реальний час; для демонстрації додайте `PZIR_TIME_SCALE=10` у кожному):

```bash
.venv/bin/python processor.py              # 1. обробник
.venv/bin/python agent.py                  # 2. агент (--delay 2 - повільний виконавець)
.venv/bin/python api.py                    # 3. API і панель: http://127.0.0.1:8000/
.venv/bin/python simulator.py              # 4. джерело (--limit N - перші N рядків)
```

Незалежне спостереження (потрібні клієнти mosquitto; або всередині контейнера):

```bash
docker compose exec mqtt mosquitto_sub -t 'pzir/course/+/telemetry' -v
docker compose exec mqtt mosquitto_sub -t 'pzir/course/+/command' -t 'pzir/course/+/ack' -v
```

Усе разом з журналами (за ×10 сценарій триває ≈ 56 с):

```bash
scripts/demo.sh 10                                 # норма
NO_AGENT=1 LIMIT=60 scripts/demo.sh 10             # T7: агент вимкнено -> expired / unknown
BROKER_RESTART_AT=20 DEMO_TAIL_S=6 scripts/demo.sh 10   # T8: перезапуск брокера посеред сценарію
```

Тести: `.venv/bin/python -m unittest discover -s tests -v`

### Масштаб часу

`PZIR_TIME_SCALE=k` ділить на k усі тривалості: утримання 180 с, розрив 15 с, свіжість давача 15 с,
вік події 60 с, TTL команди 10 с. Симулятор публікує в k разів частіше. Пороги ppm не змінюються.
`observed_at` завжди дорівнює фактичному UTC-часу публікації. Масштаб видно в панелі та в `/state`.
Оцінюваний режим — `k=1`, а `k=10` використовується лише для показу.

## Хмара: AWS IoT Core

Брокером може бути локальний Mosquitto або **AWS IoT Core** (регіон eu-north-1). Модель ESP8266 у контейнері `hw` публікує телеметрію прямо в хмару, а обробник і панель отримують її звідти. Перемикання між брокерами відбувається через `.env`: файл підхоплює `config.py`, а `docker compose` бере з нього `PZIR_BROKER_HOST`.

```bash
aws login --profile lpnu                        # тимчасові облікові дані з консолі AWS
AWS_PROFILE=lpnu scripts/aws_setup.sh           # Thing, сертифікати, політики, правила, панель (повторний запуск безпечний)
.venv/bin/python scripts/check_broker.py        # mTLS-з'єднання: публікація -> отримання, ≈ 120 мс
HW=1 scripts/demo.sh 1                          # емульоване залізо -> AWS IoT -> обробник -> команда -> реле
PZIR_BROKER_HOST=127.0.0.1 PZIR_BROKER_PORT=1883 PZIR_BROKER_TLS=0 scripts/demo.sh 10   # знову локальний брокер
```

Що створює `scripts/aws_setup.sh`:
- **Thing `class-20`.**
- **Два сертифікати X.509** (вузол і сервер). Закриті ключі лишаються лише в `certs/`, який не потрапляє в git.
- **IoT Policy `co2vent-node`.** Дозволяє клієнти `esp8266-class-20`, `co2vent-agent` і `co2vent-simulator`; публікацію лише в `telemetry`, `ack` і `state` свого класу; підписку лише на `command`.
- **IoT Policy `co2vent-server`.** Дозволяє клієнт `co2vent-processor` і доступ до `pzir/course/*`.
- **Правила IoT → CloudWatch.** Метрики `CO2Vent/scd40-1..3` (ppm) і `CO2Vent/ventilation` (1/0 за ACK) дають графіки. Журнал усіх повідомлень іде в `/co2vent/mqtt` (зберігається 30 днів). Помилки самих правил пишуться в той самий журнал.
- **Панель CloudWatch `co2vent`.** На ній CO₂ за давачами з порогами 1000 і 800 ppm, стан вентиляції й таблиця команд та ACK.

Особливості AWS IoT, які довелося врахувати:
- **Автентифікація.** Лише взаємний TLS із сертифікатом клієнта, без логіна й пароля.
- **Порядок доставки не гарантований.** На старті прогону три події прийшли в зворотному порядку, тому з'явилася політика `late`, описана вище.
- **SQL правил.** `value` — зарезервоване слово, тому значення береться через `get(*, 'value')`. Шаблони дій не підтримують `CASE`, тому стан вентиляції обробляють два правила з константами.

**Затримки через хмару** (за `logs/SUMMARY.md`) вимірювались від локальної машини у Львові до eu-north-1:

| Шлях | Медіана | p95 |
|---|---|---|
| Телеметрія | 80–114 мс | 129–146 мс |
| Команда → ACK | 73–138 мс | ≤ 142 мс |

Поріг К6 (≤ 100 мс для телеметрії) визначено для локального брокера. Для хмари він не діє, бо одна мережева подорож туди й назад займає ≈ 60–120 мс.

**Вартість.** IoT Core коштує $1 за 1 млн повідомлень і $0,08 за 1 млн хвилин з'єднання; правила — $0,15 за 1 млн. Цілодобова робота обійшлася б ≈ $3 на місяць, прогони курсової — центи. Усе покривають кредити Free plan, а метрики й журнал вкладаються в безкоштовні ліміти CloudWatch.

## Хмарні прогони за запитом (ECS Fargate)

Увесь стенд (емульоване залізо, обробник і вебпанель) може працювати в AWS і запускатися кнопкою. У простої жоден обчислювальний ресурс не працює.

```
браузер → API Gateway (HTTPS, обмеження 2 запити/с)
   GET  /        сторінка керування
   POST /run     ┐
   GET  /status  ├ лише з токеном Cognito (Hosted UI, PKCE; користувачів створює тільки адміністратор)
   POST /stop    ┘
   GET  /panel/dashboard   вебпанель прогону через той самий HTTPS-домен (лише з IP, що запустив прогін)
      → Lambda co2vent-control → ECS Fargate (ARM64, 1 vCPU / 2 ГБ), образ cloud/Dockerfile:
           сертифікати з SSM → прошивка Uno в simavr + моделі → AWS IoT Core → обробник + панель :8000
           панель :8000 ← Lambda co2vent-panel-proxy (у VPC; єдине джерело, якому відкрито порт)
           → результати в S3 (runs/, зберігаються 30 днів) → контейнер зупиняється
```

```bash
AWS_PROFILE=lpnu BUDGET_EMAIL=<пошта> scripts/aws_deploy.sh     # бакет, SSM, образ в ECR, Lambda, стек cloud/stack.yaml, бюджет
aws cognito-idp admin-create-user --user-pool-id <UserPoolId> --username <пошта> \
    --user-attributes Name=email,Value=<пошта> Name=email_verified,Value=true --desired-delivery-mediums EMAIL
```

Далі відкрий `ControlUrl`, увійди, обери режим («норма ×10», «з відмовами ×10» або «реальний час ×1») і натисни «Запустити».

**Захист:**
- маршрути керування без JWT повертають 401;
- одночасно може йти лише один прогін;
- вебпанель доступна лише через `…/panel/dashboard` і лише з IP того, хто запустив прогін; IP контейнера назовні не видно;
- порт 8000 контейнера відкритий тільки для групи безпеки проксі-Lambda у VPC, а сама панель ще й вимагає випадковий ключ прогону (`X-Panel-Key`);
- контейнер має жорсткий ліміт часу `MAX_RUN_S` = 1500 с;
- бюджет надсилає сповіщення про будь-які витрати понад $0,01 без урахування кредитів;
- сертифікати лежать у SSM як SecureString, а не в образі.

**Вартість:** ≈ $0,005 за прогін ×10 (Fargate + публічна IPv4). У простої ≈ $0,05 на місяць (ECR, S3).

## Емульоване залізо

```bash
docker compose build hw                         # один раз (~2 хв): arduino-cli, ядро AVR, simavr
HW=1 scripts/demo.sh 10                         # норма, ×10
HW=1 HW_RESET_AT=42 HW_WIFI_DROP=15:6 HW_CRC_FAULTS="scd40-2:20" scripts/demo.sh 10   # відмови
PZIR_TIME_SCALE=1 docker compose --profile hw up hw   # лише залізо, реальний час (сервер - вручну)
docker compose exec hw sh -c 'kill -USR1 $(cat /tmp/uno_sim.pid)'   # кнопка RESET на Uno
```

Журнали `logs/run-*-hw*/hw/`:
- `firmware-build.log` — розмір прошивки: 6,7 КБ flash (20 %), 522 Б RAM (25 %);
- `uno_sim.log` — перемикання піна реле D7, скидання, фактична швидкість симуляції;
- `i2c.log` — підключення моделей шини та вставки несправностей;
- `esp.log` — Wi‑Fi, NTP, черга, команди, помилки давачів.

Протокол UART (9600 8N1, рядок ≤ 48 символів) описано в заголовку прошивки:
- `S,<seq>,<канал>,<ppm>,<t·100>,<rh·100>` — вимірювання;
- `E,<канал>,nack|crc|mux` — помилка давача;
- `B` — плата запустилась і готова;
- `H,<uptime>,<реле>` — heartbeat раз на 10 с;
- `C,<id>,<0|1>` → `A,<id>,applied,<стан>` — команда й відповідь;
- `X,badline|overflow` — відхилений рядок.

Після скидання Uno ESP публікує `pzir/course/<id>/state` з `node_boot` (реле вимкнене). Після власного старту, за першим heartbeat, ESP публікує `node_sync`. Обробник оновлює за цим звітом підтверджений стан і повторює потрібну команду.

**Наскільки емуляція близька до реальної плати**

| Шар | Як у реальності | Чим відрізняється |
|---|---|---|
| Прошивка Uno | той самий `.elf`, інструкції ATmega328P, ліміти flash і RAM, Wire, Timer0, USART, sleep | таймінги периферії simavr спрощені |
| SCD40 / TCA9548A | адреси, команди, CRC‑8, 5 с, 500 мс після stop, NACK у periodic-режимі | значення CO₂ задає сценарій; немає прогріву, ASC/FRC, впливу T/RH, електрики шини. Припущення: NACK при читанні без готових даних — перевірити на реальному давачі |
| UART Uno ↔ ESP | ті самі байти й обмеження рядка | немає помилок бод, завад і узгодження 5 В ↔ 3,3 В. На реальному Uno UART0 спільний з USB |
| ESP8266 | обмеження lwmqtt: пакет ≤ 512 Б, QoS 1, clean session; черга 16; дедуплікація 16; NTP | це модель прошивки, а не емуляція чипа. Wi‑Fi, DHCP, живлення (піки 300+ мА) і reset ROM не моделюються |
| Сервер, БД, API | без змін | — |

**Що виявила емуляція (і що виправлено)**
1. **ESP пропускав рядок `B`,** бо стартує пізніше за Uno. Додано heartbeat `H` і синхронізацію `node_sync` та `node_boot` за uptime.
2. **Команда, надіслана одразу після скидання, протерміновувалась,** бо Uno ще виконував `setup()` (≈1,5 с на ініціалізацію давачів). Тому `B` тепер друкується наприкінці `setup()` і означає готовність приймати команди.
3. **Після скидання реле вимкнене, а сервер вважав вентиляцію ввімкненою.** Звіт `state` виправляє це за ≈2 с симульованого часу (`logs/run-*-hw-unoreset-*`).
4. **JSON телеметрії займає понад 256 Б.** PubSubClient із буфером за замовчуванням його не надішле, а `MQTTClient(512)` надсилає (`test_esp_bridge`).

**Для маршруту Б (реальна плата)** лишається:
- прошити той самий `.ino`;
- зібрати схему: TCA9548A, узгодження рівнів, окреме живлення 3,3 В для ESP;
- написати прошивку ESP8266 з тими самими обмеженнями (arduino-mqtt, NTP, черга);
- змінити `source` на `sensor`;
- перевірити прогрів і калібрування SCD40.

## Контракт

Теми: `pzir/course/<device_id>/telemetry | command | ack`, QoS 1.

```json
{"schema_version":1,"event_id":"<uuid4>","device_id":"class-20","sensor_id":"scd40-2",
 "observed_at":"2026-12-01T09:00:00.000Z","metric":"co2","value":1012.5,"unit":"ppm","source":"simulated"}
{"command_id":"cmd-4dae99a4adb5","device_id":"class-20","action":"ventilation_on",
 "issued_at":"…Z","expires_at":"…Z"}
{"command_id":"cmd-4dae99a4adb5","device_id":"class-20","status":"applied","ack_at":"…Z","ventilation":"on"}
```

Обробник перевіряє повідомлення в такому порядку, і перша невдала перевірка дає запис у `rejected` з причиною:
1. розмір ≤ 1024 Б і валідний JSON-об'єкт;
2. дубль `event_id`;
3. точний склад полів і `schema_version`;
4. формат ідентифікаторів;
5. `device_id` у payload збігається з темою;
6. `sensor_id` ∈ {scd40-1..3}, `metric=co2`, `unit=ppm`, `source` з переліку;
7. `value` — скінченне число 0…40000 (вихідний діапазон SCD40; специфікована точність 400–2000 ppm);
8. `observed_at` має зону, не старший за 60 с і не з майбутнього понад 5 с;
9. для кожного давача час має зростати. Подія, що прийшла не в порядку, але не застаріла, зберігається в історії з позначкою `late`, а правило й медіана її не враховують. Причина: AWS IoT Core не гарантує порядку доставки.

**Агрегація.** Береться медіана останніх показів давачів, свіжих у межах ±15 с від поточної події. Для рішення потрібні щонайменше 2 давачі. Медіана не реагує на один «залиплий» давач.

**Автомат стану.**
- **OFF → ON:** медіана > 1000 тримається ≥ 180 с без перерви. Рівно 1000 не вважається перевищенням і скидає відлік.
- **ON → OFF:** медіана < 800. Рівно 800 не зупиняє, а в зоні 800…1000 вентиляція залишається ввімкненою.
- **Пропуски:** відсутність рішення не рахується нормою. Якщо валідних рішень не було понад 15 с, відлік скидається.
- **Відновлення:** стан правила зберігається в `rule_state` і відновлюється після перезапуску.

**Команди.** Правило змінює лише бажаний стан вентиляції. Підтверджений стан виконавця змінюється тільки після ACK. Якщо ці два стани розходяться і відкритої команди немає, обробник видає нову команду.

- **Життєвий цикл:** `created → sent → applied | rejected | expired`.
- **Запізнілий ACK:** ACK, що прийшов після `expires_at`, не робить команду `applied`.
- **Що показує інтерфейс:** `pending`, поки чекаємо ACK; `unknown` після тайм-ауту; `on/off` — лише за ACK.
- **Перший запуск:** стан виконавця невідомий, тому перша ж подія приводить його в безпечний `off`.

## Зміни у v1.1

У прогоні без агента у версії `v1.0` (`logs/run-20261030T152629Z-x10-noagent`) одну команду з семи позначено `expired` через 503 мс після дедлайну. Це перевищує допуск К4 (0,5 с), бо `sweep()` викликався раз на 0,5 с. Що змінено у `v1.1`:
- **Частіша перевірка тайм-аутів.** `sweep()` тепер викликається раз на 0,1 с (`SWEEP_PERIOD_S`).
- **Панель не чекає `sweep()`.** `ventilation_view` показує `unknown`, щойно минув `expires_at`.
- **Момент закриття фіксується.** Обробник записує в `commands.closed_at`, коли закрив команду. Тепер запізнення вимірюється, а не оцінюється.

Повторні прогони без агента (×10 і ×1) дали 13 прострочених команд із запізненням 0…91 мс.

## Обмеження прототипу

- **Дані модельовані.** `source=simulated`, тому фізичної верифікації SCD40, калібрування (ASC/FRC) та впливу температури й вологості немає.
- **Реальна схема.** Для фізичного варіанта потрібні:
  - мультиплексор I²C TCA9548A, бо адреса SCD40 фіксована (0x62);
  - узгодження рівнів 5 В ↔ 3,3 В для ESP8266;
  - окреме живлення ESP.
- **Ідемпотентність на Uno.** Uno не має довговічного журналу `command_id`, тому на реальній платі вона була б обмеженою (методичка, п. 5.3).
- **Безпека брокера.** Локальний Mosquitto працює без TLS і ACL і слухає лише 127.0.0.1. В AWS IoT Core є взаємний TLS із сертифікатами X.509 і політики з мінімальними правами. HMAC-підпис команд (як у ЛР6) поки не додано.
- **mTLS на реальному ESP8266.** TLS із клієнтським сертифікатом (BearSSL) забирає помітну частину вільної RAM ESP8266, порядку десятків кілобайт. Модель ESP цього не перевіряє, тож на реальній платі це треба виміряти.
- **Повтор команд при недоступному агенті.** Нова команда видається на першій події після тайм-ауту попередньої, тобто приблизно раз на TTL + період.
- **Публікація й запис у БД.** Це не одна транзакція. Команда, що залишилась у стані `created`, досилається в `recover()` під час старту.
- **Залишки сесій у брокері.** Якщо `hw` працює без обробника, брокер накопичує телеметрію для постійної сесії обробника. Після старту обробник відхилить її як `stale`. Для чистого прогону перезапустіть брокер (`docker compose restart mqtt`).
- **Сесії MQTT.** У обробника й агента `clean_session=False`, тому брокер доставляє команди, накопичені за відсутності агента. Агент відхиляє прострочені з них (`rejected expired`), що видно в `logs/run-*-brokerrestart/agent.log`. Сесії живуть у пам'яті брокера, бо persistence вимкнено.
